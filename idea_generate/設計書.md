# Idea Research Workspace Phase 1 設計書

## 1. 目的

本システムは、ユーザーが日常的に記録した研究アイデア・仮説・実験結果・疑問点を入力として受け取り、それらを少数の再利用可能な概念へ圧縮し、現在の研究状態を整理した上で「次に検証すべき実験」を提案する。

Phase 1では、以下の能力に限定する。

1. 生のアイデアメモを構造化する
2. 類似・重複するメモを統合する
3. 上位概念へ圧縮する
4. 仮説・既知事項・未検証事項を分離する
5. 次の実験候補を生成する
6. 情報利得・重要度・コストから優先順位をつける
7. 人間が理解できる研究サマリを出力する

最終目標は「文章を短くする要約器」ではなく、研究状態を内部表現として保持し、次の行動を選択できる Research Workspace を構築することである。

---

# 2. Phase 1 の検証仮説

## H1

生のアイデアメモ群は、意味的情報を大きく失うことなく、少数の概念へ圧縮できる。

## H2

圧縮された概念表現を用いることで、生メモを直接参照する場合よりも未解決問題を効率よく特定できる。

## H3

未解決問題・不確実性・依存関係を利用することで、妥当な「次の実験」を提案できる。

## H4

単純なLLM要約よりも、構造化された概念グラフを経由した方式の方が、過去の研究との重複・矛盾・未検証事項を発見しやすい。

---

# 3. 対象データ

最初の検証では、50〜100件程度の研究メモを使用する。

メモには以下が混在していてよい。

* アイデア
* 疑問
* 仮説
* 実験案
* 実験結果
* 観察
* 反例
* 方針変更
* 将来やりたいこと
* 他のアイデアとの関連

入力例：

「未知UIでも座標に依存せず操作できるようにしたい。affordanceで表現すればいけるかもしれない。既知UIではSELECTやTRANSFERはできたが未知UIはまだ試していない。」

# 7. 概念圧縮

Phase 1では完全な自律概念発見は狙わず、

1. semantic similarity
2. 共通subject
3. 共通relation
4. 共通prediction
5. 圧縮率

を利用する。

概念候補 C に対して、

```text
score(C)
 =
 similarity
 + reuse
 + predictive_value
 - complexity
```

を計算する。

より研究的に扱う場合、

$$
L = L(C) + L(D|C)
$$

というMDL基準を使う。

ここで、

* \(D\)：元メモ・AtomicClaim
* \(C\)：概念集合
* \(L(C)\)：概念自体の記述量
* \(L(D|C)\)：概念を使って元データを説明する残差

とする。

概念を作ることで

$$
\Delta L
=
L_{\mathrm{before}}
-
L_{\mathrm{after}}
$$

が正なら、その概念を保存候補とする。

# 9. Research State

システムは現在の研究状態を次の4種類へ整理する。

```python
@dataclass
class ResearchState:

    established: list[str]

    hypotheses: list[str]

    unresolved: list[str]

    contradictions: list[str]
```

### Established

すでに実験などで支持されたもの。

### Hypotheses

まだ十分に検証されていない主張。

### Unresolved

重要だが答えがない問題。

### Contradictions

複数のメモ・実験結果の間で整合しない事項。

# 10. Gap Detector

「次に何を検証するべきか」の候補を作るため、研究グラフからギャップを抽出する。

対象：

```text
prediction があるが test がない
hypothesis があるが evidence がない
結果同士が矛盾している
重要Conceptに unresolved question がある
依存先の仮説が未検証
```

例：

```text
Concept:
Functional Affordance

prediction:
未知UIへ転移可能

tested_by:
なし
```

この場合、

```text
Research Gap:
未知UIへのzero-shot転移が未検証
```

を生成する。

# 11. Experiment Generator

Research Gapから実験案を作る。

実験は以下の形式に統一する。

```python
@dataclass
class ExperimentProposal:

    id: str

    title: str

    target_hypothesis: str

    intervention: str

    control_condition: str

    expected_result: str

    falsification_condition: str

    metrics: list[str]

    estimated_cost: float
```

例：

```text
Title:
未知UI Zero-shot Transfer

Hypothesis:
affordance表現は未知UIへの転移能力を改善する

Conditions:

A:
座標ベース

B:
object IDベース

C:
affordanceベース

Metric:
task success rate
first-action accuracy
regret
replanning count

支持条件:
C > A, B

棄却条件:
C <= A
```

# 12. Experiment Ranker

複数の実験候補から優先度を決定する。

基本スコア：

$$
Score(e)
=
w_uU
+
w_iI
+
w_nN
+
w_dD
-
w_cC
$$

各項目：

### U: Uncertainty

現在どれだけ不確実か。

### I: Information Gain

結果によって研究状態がどれだけ変わるか。

### N: Novelty

既存実験とどれだけ異なるか。

### D: Dependency Impact

この仮説が他の仮説の前提になっている度合い。

### C: Cost

実装・計算・人的コスト。

初期値：

```python
weights = {
    "uncertainty": 1.0,
    "information_gain": 1.5,
    "novelty": 0.5,
    "dependency": 1.0,
    "cost": 0.7
}
```

# 13. Conscious Workspace

意識モデルとの接続点。

すべてのResearch GapやExperimentを同時に処理するのではなく、有限容量のWorkspaceへ候補を投入する。

例：

```python
WORKSPACE_SIZE = 8
```

候補ごとのsalience：

$$
S
=
uncertainty
+
importance
+
information\ gain
+
novelty
-
cost
$$

上位K個だけをWorkspaceへbroadcastする。

```text
Long-term Research Graph
        ↓
candidate gaps
        ↓
Salience Competition
        ↓
Finite Workspace
        ↓
Experiment Decision
```

これによって、

「知っているすべてを考える」

のではなく、

「現在重要な研究課題だけを意識上へ出す」

構造にする。

# 16. 最初の実装ではLLMに任せる部分

Phase 1では自然言語処理部分をすべて自作する必要はない。

LLMを以下だけに限定して利用する。

```text
文章
 ↓ LLM
AtomicClaim JSON

Research Gap
 ↓ LLM
ExperimentProposal JSON

 ↓ LLM

```

重要なのは、

```text

```

をLLMだけに決めさせないことである。

これらはResearch Graph・MDL・スコアリング側で処理する。

# 18. Phase 1のベンチマーク

最低限、以下を測定する。

## Compression Ratio

$$
CR =
\frac{N_{concept}}
{N_{claim}}
$$

例：

```text
100 claims
→
18 concepts

CR = 0.18
```

---

## Reconstruction Coverage

Concept群から元Claimをどれだけ説明できるか。

```text
covered claims / total claims
```

目標：

```text
>= 0.8
```

---

## Duplicate Reduction

同じ意味のClaimを何件統合できたか。

---

## Gap Precision

モデルが「未検証」と判定したものについて、人間が本当に未検証と判断する割合。

---

## Experiment Relevance

提案された実験について、

```text
0 = 無関係
1 = 弱い
2 = 有用
3 = 次に実施したい
```

で人間評価する。

---

## Top-1 Agreement

ユーザー自身が選んだ次の実験とシステムのTop-1が一致した割合。

これは非常に重要な指標とする。

---

# 19. 比較実験

以下の3条件を比較する。

```text
A:
Raw Note → LLM summary → experiment

B:
Atomic Claims → LLM → experiment

C:
Atomic Claims
→ Concept Compression
→ Research Graph
→ Workspace
→ experiment
```

主比較：

```text
A vs C
```

評価：

```text
未検証事項発見率
重複実験提案率
人間評価
Top-1 Agreement
使用token数
処理時間
```

CがAより優れていれば、

「概念圧縮＋研究状態表現が研究判断に寄与した」

という証拠になる。

# 21. Phase 1成功条件

最低成功条件：

```text
50〜100件のメモを処理可能

AtomicClaim生成成功率 > 95%

Concept数 < Claim数の50%

Reconstruction Coverage > 80%

未検証事項を複数抽出可能

実験候補3件以上生成可能

各実験に棄却条件が存在する
```

研究的成功条件：

```text

    >
Concept Compressionなし
```

が、

```text
Experiment Relevance

Top-1 Agreement
```

のどちらかで再現性をもって観測されること。

# 25. Phase 1完了後

Phase 1で有効性が確認された場合、Phase 2では実験結果を再入力する。

```text
Experiment Proposal
        ↓
experiment
        ↓
Result
        ↓
Research Graph update
        ↓
Concept confidence update
        ↓
new Research Gap
        ↓
next experiment
```

これにより、

```text
IDEA
 ↓
HYPOTHESIS
 ↓
EXPERIMENT
 ↓
RESULT
 ↓
CONCEPT REVISION
 ↓
NEXT EXPERIMENT
```

という自己更新型研究ループを形成する。

Phase 1の本質的な検証対象は、

「アイデアをうまく要約できるか」

ではなく、

「圧縮された概念表現が、次に行う研究判断を改善するか」

である。
